# 大肥鱼的异世界转生勇者冒险：独立测试原型

本版本没有接入 QQ、没有注册接收器、没有修改或重启 Tulpa/NapCat，
没有对正式 `data/asmr-support.sqlite3` 作任何迁移。
单元验收默认离线，CLI试玩默认使用真实 DeepSeek。

## 本地验证与试玩

当前使用群共享版终端交互聊天，网页服务已停止。运行：

```bash
cd /home/summer/Tulpa
.venv-linux/bin/python scripts/adventure_cli.py
```

默认真实DeepSeek，由你亲自输入消息，没有模拟玩家。
“冒险”查看或生成本群事件，随后直接描述你的方案。不再提供逃跑。
“状态”“背包”“帮助”查询，“退出”结束。再次运行会继续同一位测试勇者。
终端状态位于 `.tmp/adventure-sandbox/live.sqlite3`，与此前网页测试勇者分开。
可通过 `--player sandbox:名字` 创建不同测试勇者，默认同属 `sandbox:group`，共享每日3个事件。
增加 `--group 群标识` 可模拟另一个群。

### 当前群共享规则（取代下文旧个人版规则）

- 每群北京时间每天最多3个事件，包含首次生成；没有参与者时按下次输入“冒险”懒生成，不做后台模型调用。
- 同群所有人看到同一事件。难度参考首次开启该事件的勇者等级，生成后固定；
  各人使用自己的等级、属性和背包应对。共享场景不能要求参考玩家独有的物品。
- 一人成功后只向该人发奖，自动生成下一事件；第三个成功后停止刷新。
- 失败清零该人的等级和背包，事件保留，其他群友或该玩家都可继续尝试。
- 未解决事件次日过期，不发奖、不扣任何人的等级，不占第二天名额。
- 普通事件只在生成时花生成费用，同一场景查询/换玩家不重复生成。
  每次实际行动仍需模型评估与结局调用，不代表每日总请求数只有3次。
- 同一时刻一个事件只能由一人结算，防止并发重复发奖；跨天旧事件不能补发奖励。
- 最终Boss仍为100级玩家的个人挑战，不受群3事件额度限制，也不触发普通群事件刷新。
- 旧个人版已经获得的等级、物品保留；其未完成普通场景退休，转入新群共享场景。
- 仍是CLI本地试玩，正式群助手尚未接入游戏。

以下网页方式为先前实现，当前未运行：<http://127.0.0.1:7864/>。
点击“开始冒险”，阅读真实DeepSeek场景，在输入框自由描述行动，选择执行或逃跑。
没有自动模拟玩家；等级、属性、背包、剩余次数及最近结局都会显示。
浏览器通过本地Cookie识别自己的测试勇者，状态存于独立的
`.tmp/adventure-playtest/players.sqlite3`；试玩费用记在同目录`costs.sqlite3`。
关闭页面仍保留进度，清除Cookie或换浏览器会得到另一名测试勇者。
每日3次按正式规则执行，正式QQ入口尚未开启。

页面服务启动与管理：

```bash
bash scripts/adventure-playtest.sh start
bash scripts/adventure-playtest.sh status
bash scripts/adventure-playtest.sh stop
```

服务为 `tulpa-adventure-playtest.service`，独立后台运行，目前没有设置开机启动。

在 `/home/summer/Tulpa` 运行：

```bash
.venv-linux/bin/python scripts/check_adventure.py
.venv-linux/bin/python scripts/adventure_cli.py demo
.venv-linux/bin/python scripts/adventure_cli.py demo --offline
.venv-linux/bin/python scripts/check_adventure_live.py
```

`demo` 使用真实 DeepSeek 连续试玩三轮：普通行动、荒诞行动、逃跑。
模拟玩家的行动也由模型生成，主持、评估、结算流程使用实际游戏代码与随机数。
每轮检查次数、升级、死亡清零及重启后幂等；在测试目录保存完整JSON报告。
`demo --offline` 才是临时数据库中的固定样例，不代表实际模型质量。
单元验收测试使用临时 SQLite 和 MockTransport，
验证 DeepSeek 请求格式、费用结算及游戏状态流程，不访问网络。
`check_adventure_live.py` 使用真实模型评估4个人工构造的场景，检查水属性克制、
固定Boss弱点和两种不合理行动，不将这些人工场景混称为随机生成事件。

真实模型试玩使用现有 `.env` / 环境变量中的 DeepSeek 配置，`--live` 仍兼容。
无需在命令行提供或打印密钥；只发送虚构角色、事件和玩家输入，不发送群记录或项目知识。

```bash
.venv-linux/bin/python scripts/adventure_cli.py start --live --player sandbox:alice --request-id day1-start
.venv-linux/bin/python scripts/adventure_cli.py act --live --player sandbox:alice --request-id day1-act --action '利用场景里的绳索绕到敌人背后。'
.venv-linux/bin/python scripts/adventure_cli.py status --live --player sandbox:alice
.venv-linux/bin/python scripts/adventure_cli.py flee --live --player sandbox:alice --request-id escape1 --action '制造烟雾后沿来路逃走。'
```

先读实际生成的事件，再输入适合它的行动；以上行动仅为命令示例。相同消息重放应使用相同
`--request-id`。默认玩家为 `sandbox:demo`，可换玩家验证隔离；`--offline` 使用固定离线模型。

试玩库位于 `.tmp/adventure-sandbox/live.sqlite3` 或 `offline.sqlite3`，
模型测试费用单独记在 `test-costs.sqlite3`，沿用现有费用预留/结算机制与闲聊预算限制。
该测试账本不属于生产群助手每日总预算，真实试玩会额外消耗账号余额。
生成一次事件1次调用；行动评估与叙事各1次调用。查询、重复消息不调用模型。
自动三轮demo额外每轮1次模拟玩家行动生成，预计共12次请求。

## 持久状态与幂等

- 玩家键未来采用 `qq:<机器人账号>:<用户QQ>`；同一机器人下跨群共享等级与每天次数。
  身份来自消息元数据，不接受正文指定他人身份。
- `adventure_players.state` 是 JSON，保存等级、5项属性、背包和转生轮次。
  另外保存北京时间日期、已用次数、当前事件ID。
- `adventure_attempts` 保存事件、开始时状态快照、秘密随机数、原行动、处理阶段和结算。
  `adventure_actions` 对消息ID去重。记录用于恢复和幂等，不维护成就/死法图鉴。
- 每天北京时间00:00恢复3次；事件开始就占一次。跨天未完成事件保留，仍计入开始那天。
- 开始事件和数值结算使用 SQLite `BEGIN IMMEDIATE` 原子事务；网络调用在事务外进行。
  单个用户只能有一个未完成事件，其他用户可独立处理。
- 秘密随机数在开始时固定，行动评估时不提供给模型。重试不会重新抽敌人或掷骰。
- 已完成结果可重复读取但不能重复发奖。结算在叙事前落库，叙事失败使用简短固定结局。
- 模型响应错误不算玩家失败，也不清零；保留事件和原行动，使用 `retry --live` 显式重试。
  已扣/未知费用保留账本，不自动重放。
- **进程恰好在模型调用中退出**时，generating/evaluating保持待人工核查，原型拒绝自动重放。
  正式接入前需补充管理员恢复入口或调用租约，不能直接将它当作玩家死亡。

## 程序控制的规则

初始Lv.0、五项属性各5。测试版本属性采用 `5+等级` 的简单成长公式，
先验证状态与结算；职业、差异化属性成长、消耗品耐久不属于本版。

成功：普通/杂鱼+1、困难+2、极难/最终Boss+3。逃跑成功+0，保留状态；
挑战或逃跑失败清零等级、恢复初始属性、清空背包，转生轮次+1，不补次数。
背包最多30件，满了继续升级但不收取新物品。

随机事件：15%杂鱼、60%普通、20%困难、5%极难。敌人等级按玩家等级递增，
杂鱼约为玩家等级的20%。低等级仍受算法限制。难度在事件生成前由程序决定。

称号从当前等级计算：20初露锋芒的勇者、30王国认证勇者、50异世界传奇、
70魔王的头号麻烦、100大肥鱼钦定救世主。清零后恢复初来乍到；不保存称号成就，
也不调用QQ群头衔接口。

最终Boss通过 `start --live --boss` 主动挑战，100级解锁。
`chatlocal/adventure.py` 的 `FINAL_BOSS` 固定其120级、五项属性、技能与3个弱点；
本版用等级决定综合战力，固定五项Boss属性提供叙事依据。
模型不能更换Boss名称、技能、弱点；需在评估中指出实际利用的固定弱点。
没有利用弱点的正面战斗胜率最高10%，运用有效弱点显著加成。
本版是单次方案结算，多阶段战斗和通关后的循环玩法尚未实现。

## 模型与数值的边界

1. 生成：接收状态、程序选定的难度和敌人等级，返回场景、敌人特点和可利用线索。
2. 评估：接收场景、玩家自由行动、背包，返回normal/absurd、因果可行性、相关属性、
   已有物品的实际作用、固定Boss弱点与拟定奖励。程序校验枚举、物品ID、文本长度和弱点。
3. 程序：计算概率、用预存随机数判定、升级或清零、保存奖励。
4. 叙事：接收已确定结算，写短结局。前端/机器人显示的数值始终取程序结果。

数值相当时合理常规方案基础85%，有场景依据的荒诞方案基础40%；
勉强方案基础更低，高属性可弥补差距。物品克制最多增加15个百分点，
幸运可适度帮助荒诞方案或逃跑；缺乏关键条件的impossible方案概率为0。
普通可行性概率限制2%至98%，显式不可能方案除外。

物品保存 `id/name/nature/origin/rarity`，不保存攻击力等固定战斗数值。
例如水之剑的nature是“凝聚流动清水”，对火系敌人或灭火方案可以加成，
不能因玩家一句话变成无限许愿剑。荒诞成功奖励标为奇珍，并由模型构思奇异用途；
本版尚未实现不同稀有度的专属效果上限。

实际语义（道具是否克制、荒诞方案是否可行、结局是否严格一致）仍依赖模型判断。
已执行真实三轮试玩与专项判定；这属于抽样验证，不能证明所有生成内容都正确。
真实试玩发现结局曾临时添加场景外的致命危险，已收紧叙事提示，提供评估因果依据，
并限制结局长度；正式上线前仍应人工关注场景一致性与难度体验。

`@机器人 行动 <描述>`、`@机器人 逃跑 <描述>`、`@机器人 状态`。
保留现有“@其他人不回复”的规则；普通群消息不当作游戏行动，也不生成Bug。
群身份/用户ID/消息ID取现有接收器，使用已有发送审核和幂等发送流程，不启动第二个QQ接收器。
游戏独立于每人5小时100条闲聊额度，但生产模型调用须复用正式共享费用账本，
不能使用测试账本扩大生产预算。所有入口应默认关闭，在试玩验证后再启用指定群。
