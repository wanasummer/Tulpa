# ASMRTranslator QQ 支持机器人设计草案

日期：2026-10-05。状态：初版已实现，使用方法与当前限制见 [ASMR_SUPPORT.md](ASMR_SUPPORT.md)；尚未接入真实群聊。下文保留设计方向，超出初版的能力仍为后续计划。

最新执行策略：完整答复经过程序检查与独立 DeepSeek 审核后自动发送，无人工逐条审批；不通过或审核不可用时默认拦截。Bug 分析先写入默认 SQLite 群助手库，审核拦截不丢工单。生成与审核共享每日5元额度。在线答疑已停用直接源码检索，源码索引仅保留在本地；文档过滤和模型审核不提供绝对保密保证。

## 已确认的目标

- 在本机运行，以 DeepSeek 回答 QQ 群友的 ASMRTranslator 使用问题。
- 技术答疑优先，可以适量参与日常聊天。
- 面向普通用户提供界面操作与解决步骤，不要求用户阅读代码。
- 自动整理 Bug，供维护者查看和处理。
- 每日额度按 API 花费计算，固定为人民币5元，只展示，不增加额度配置。
- 当前知识来源仅为项目 README、前后端代码、所选 QQ 群的文档；FAQ 与已解决 Bug 库暂不存在。

## 现有实现与缺口

| 能力 | 当前状态 | 本需求中的处理 |
| --- | --- | --- |
| OneBot 实时事件 | `chatlocal/onebot_events.py` 已有本机 WebSocket 接收 | 复用连接与账号检查 |
| 持续群聊 | `chatlocal/mcp_chat.py` 有群范围、会话、游标和停止控制 | 复用协议，但补充独立后台执行器 |
| QQ 发送 | `chatlocal/mcp_actions.py`、`message_sender.py` 有持久发送回执 | 复用幂等与 UNKNOWN 状态，不盲目重发 |
| DeepSeek | `chatlocal/config.py`、`agent.py` 已有配置与调用 | 复用连接配置，单独定义客服回答契约 |
| 资料检索 | 现有聊天和聊天附件检索 | 增加面向产品文档的独立知识库 |
| 行为记忆 | 现有个人交流记忆 | 不作为产品事实或已解决 Bug 的权威来源 |
| 配额 | 当前 Agent 主要限制每轮调用、时间和上下文 | 增加跨重启持久化的每日费用账本 |
| Bug 汇总 | 未发现专门客服工单闭环 | 增加工单、去重、状态和本地汇总 |

`doc/MCP.md` 明确说明：现有持续群聊不调用 Tulpa 内置模型；外部 Agent 退出后也不会被自动唤醒。因此，仅配置人格或连接 DeepSeek Harness 不能完成常驻客服。

## 处理流程

QQ 消息 → 范围与去重检查 → 本地触发判断 → 技术优先队列 → 本地知识检索 → 费用预留 → DeepSeek → 回答检查 → QQ 发送回执。

问题整理与工单持久化是独立流程。发送或模型失败不应丢失原始反馈。

- 忽略机器人本人消息与重复事件；只处理维护者启用的群。
- 产品使用问题、报错、针对机器人上一条答复的追问优先。
- 闲聊只在没有待处理技术问题时参与，并受独立的消费上限和冷却时间约束。
- 首先用本地规则过滤无关消息；需要模型判断时，该分类调用也计费。
- 同一用户连续补充可以短暂合并，避免每句话都调用一次模型。
- 正在处理的闲聊模型请求通常已经产生费用；优先级不能撤销已发生的计费。
- 群消息、图片文字、文档正文都属于资料，不能修改预算、目标群和机器人权限。

## 本地知识库

建立本地 SQLite 索引。第一版从项目 README、前后端源码和所选群文档进行关键词与全文检索；向量检索作为后续可替换选项，不作为启动前提。

当前索引保存来源、类型、群范围、正文和定位信息。产品版本范围、确认状态与适用环境作为后续结构化整理方向。

- 文档先整理成面向用户的步骤：在哪里点击、要填写什么、成功后看到什么。
- 已解决 Bug 记录症状、受影响版本、根因摘要、绕过方法、修复版本与确认依据。
- 新反馈先进入工单，维护者确认后才能升级为“已解决”知识。
- 根据用户版本优先检索适用资料；版本不明或资料冲突时先简短追问。
- 不把整个源代码仓库放进每轮提示词，也不以未验证的群聊猜测替代正式结论。

已只读检查桌面 `asmrTranstor/README.md`。其中存在需确认的差异，例如“三个引擎”与“五套引擎”、单文件便携版与 Tauri 安装版，以及本地处理措辞与在线服务配置。导入前应以实际发布版本核对；不把整份 README 无条件视为最新事实。

## 对群友的回答

优先给出少量可执行步骤，再问必要信息。信息不足时每轮只问最关键的几项，例如软件版本、所选引擎、出现问题的步骤或报错截图。

没有证据时明确说尚未确认，不能编造设置项、修复版本、开发者承诺或确定根因。需要代码分析的问题转换成可供维护者处理的工单。不要索取 API Key；日志与截图中的密钥和账号信息需要遮盖。

针对未解决问题可以说明“已记录，待维护者确认”，但仅在本地工单写入成功后使用这句话。不要承诺修复时间。

## Bug 工单与维护者视图

工单保存：编号、群与原消息编号、用户、软件版本、环境、操作步骤、预期结果、实际表现、错误信息、已尝试办法、知识来源、受影响人数、状态及最后更新时间。

同版本、同引擎、相似错误可以形成关联候选，保留每个用户自己的反馈；证据不足时不要强行合并。区分使用问题、疑似 Bug、已确认 Bug 与功能建议。只有维护者确认或可核验依据才能标为已确认或已修复。

维护者界面显示待补充、待确认、处理中、已解决，以及按问题聚合的每日摘要。摘要列出新增问题、重复反馈人数、仍缺信息和可追溯消息。第一版默认在本机查看；若要定时发送给维护者，需要另行指定接收位置和时间。原始工单保存不依赖付费模型，模型不可用时仍保留反馈供人工检查。

## 每日 API 费用控制

总预算固定为每日人民币5元，闲聊最多使用其中3元，统一按 Asia/Shanghai 的自然日归属；无预算输入框或额外配置项。当前采用已核对的高峰人民币单价保守计价。

- 预算覆盖分类、回答、技术追问、模型摘要、重试等全部模型请求。
- 调用前以输入用量的保守上界、最大输出和适用单价预留费用；缓存未知时按未命中价估算。无法可靠给出上界时暂停调用。
- 预留与检查放在同一数据库事务内。所有群共用每日总额度，避免并发检查通过后一起超支。
- 返回后按真实 usage 结算：缓存命中输入、未命中输入、输出分别计价；不重复计入总输入。
- 保存模型、价格版本、适用时间、计价币种和请求状态；价格变动后更新配置。若以人民币显示外币价，需要明确换算规则，不能把换算估计当作服务商实账。
- 断线、取消或超时但费用不明时保留预留并标为待核对，避免当作免费而重试。
- 重启不清零；新自然日使用新账本，跨日请求按请求准入日保留和结算，旧日未决费用仍可查看。
- 预算不足时停止新的模型调用。可以用限频固定文字提示仍接受反馈；禁止让“已达到额度”的提示刷屏。
- 技术预留不能被闲聊用掉；闲聊额度是总预算的一部分，不额外增加总预算。
- 本地账本是按配置价格和服务商 usage 计算的控制与估算，实际扣费以服务商账单为准。共用 API Key 的其他程序无法被本账本控制，建议机器人使用专用 Key。

## 建议实施顺序

1. 本地文档导入、版本化知识检索、客服草稿、Bug 工单与费用账本。先用离线群消息样本验证。
2. 后台执行器、技术优先队列、指定群自动答疑、停止开关和发送回执。
3. 闲聊人格、闲聊消费上限、维护者每日摘要；按需要再扩展图片理解。

第一版验收重点：重复消息不重复回答；同一反馈可追溯；无依据不编造解决方案；闲聊不占技术预留；并发及重启不绕过预算；UNKNOWN 发送不自动重复；群友不能用发言修改机器人配置；停止后阻止尚未派发的发送。

## 上线前仍需指定

- 目标 QQ 群、机器人账号及已有 OneBot 服务配置。
- 当前正式发布版本与项目实际位置；群文档通过目标群目录取得。
- 维护者摘要的接收位置与时间（若要自动发送）。

代码已实现固定预算与用户主动启动的执行器；本次开发未配置密钥、启动真实群机器人或发送真实 QQ 消息。
